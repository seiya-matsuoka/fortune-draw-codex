# 開発計画

## 1. 方針と前提

本計画は `AGENTS.md`、`docs/01-requirements.md`、`docs/02-design.md` に基づき、おみくじアプリを完成させるための実装工程と確認内容を定義する。

動作優先の 3 工程とし、まず抽選が動く状態を作り、その後に見た目を整え、最後に総合確認を行う。

- HTML / CSS / JavaScript の静的構成とし、外部依存、データ保存、バックエンド、デプロイは追加しない。
- 運勢は「大吉・中吉・小吉・吉・末吉・凶」の 6 種類とし、等確率で抽選する。同じ結果が連続することは正常とする。
- メッセージは各運勢に対応する短い日本語とする。具体的な文言や細かな配色は、設計書で認められた範囲で実装時に決定する。
- 各工程は個別の実装依頼を受けて進める。

## 2. 工程 1：最小構成で抽選と結果表示を実装する

### 実施内容

- リポジトリ直下に `index.html` と `script.js` を新規作成する。
- HTML に日本語指定、文字コード、viewport を設定し、タイトル、説明、抽選ボタン、結果表示領域を配置する。初期状態では未抽選であることを明示する。
- 操作には標準の `button` 要素を使う。結果領域には `aria-live="polite"` と `aria-atomic="true"` を設定し、結果更新時にフォーカスを移動しない。
- JavaScript に運勢とメッセージを組にした配列を定義する。クリック時に `Math.floor(Math.random() * 候補数)` で 1 件選び、`textContent` で表示を更新する。
- JavaScript は `defer` 付きの通常のスクリプトとして読み込み、HTML ファイルを直接開いて動作できる構成にする。CSS の作成・読み込みは工程 2 で行う。

### 確認内容

- 初期表示に必要な要素があり、未抽選の状態が分かること。
- ボタンを押すと、定義済みの運勢と対応するメッセージが表示されること。
- 繰り返し操作でき、結果領域が増殖せず更新されること。
- `Tab` でボタンへ移動し、`Enter` と `Space` でも抽選できること。
- JavaScript の実行時エラーがなく、再読み込みすると未抽選の状態に戻ること。

この工程の完了時点で、装飾前のおみくじアプリとして利用できる状態にする。

## 3. 工程 2：見た目と画面幅への対応を整える

### 実施内容

- リポジトリ直下に `style.css` を新規作成し、HTML から読み込む。
- 中央寄せ、適切な最大幅と左右の余白を基本に、タイトル・ボタン・結果を読み取りやすく配置する。
- システムフォントと少数の色を使用し、文字と背景のコントラスト、ボタンの押しやすさ、キーボードフォーカスの視認性を確保する。
- 狭い画面でも文章が折り返され、主要 UI が画面外にはみ出さないようにする。
- 外部画像、外部フォント、複雑なアニメーションは追加しない。

### 確認内容

- PC 相当の幅 1280px とスマートフォン相当の幅 375px で表示・操作できること。幅 320px でも横方向のはみ出しを確認する。
- 未抽選時と抽選後の両方で、文字の重なりや不自然な欠けがないこと。
- キーボード操作時のフォーカスが見えること。
- 見た目の変更後も、抽選と繰り返し操作が正常に動くこと。

この工程の完了時点で、主要な画面幅に対応したシンプルな UI にする。

## 4. 工程 3：総合確認と必要最小限の修正を行う

### 実施内容

- 完成したアプリを要件書・設計書と照合し、不足や不具合だけを修正する。機能追加や無関係な整理は行わない。
- 利用可能なローカルブラウザで確認する。新しい自動テスト環境や検証用ファイルは追加しない。
- 最終差分を確認し、変更内容、検証結果、未確認項目を報告する。

### 確認内容

- 6 種類すべての運勢とメッセージの対応が正しいこと。偶然すべてが出るまで待つ方法に頼らず、ブラウザ上で乱数を一時的に制御して各候補と先頭・末尾の選択を確認し、終了後は再読み込みで元に戻す。
- 通常の乱数で連続操作しても正常に動作し、同じ結果が続いても操作を妨げないこと。
- 初期表示、再読み込み、各画面幅、マウス操作、キーボード操作を通して利用できること。
- 結果領域の通知用属性と DOM 更新を確認する。スクリーンリーダーによる実機確認ができない場合は、未確認事項として明示する。
- JavaScript の実行時エラー、ファイルの読み込みエラー、意図しない外部リソース参照・通信がないこと。
- 実装が静的な 3 ファイルで動作し、要件の完了条件を満たしていること。

## 5. 工程の進め方

- 計画の確定・保存は、アプリの実装開始の許可とはみなさない。
- 実装は、ユーザーから対象工程を明示した依頼を受けて開始する。対象工程が指定されていない場合は、工程 1 を含めて実装せず、ユーザーへ確認する。
- 各工程は「指定工程の実装 → 確認 → 結果報告 → ユーザーによる確認」の単位で進め、次の工程へ自動的に進まない。
- 検証できなかった項目は完了済みとせず、理由と必要な確認を残す。
- commit、push、ブランチ操作などは、別途明示的に依頼された場合のみ行う。
